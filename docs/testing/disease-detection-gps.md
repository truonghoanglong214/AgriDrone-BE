# Disease detection GPS regression — 2026-11-12

## Failure and fix

The local AI environment did not contain `piexif`. The input photos contained GPS
EXIF, but `extract_exif_gps` swallowed the import error and the disease pipeline
substituted `(0,0)`. Matching that point to Tam Vu produced a distance of roughly
11,823,080 metres, overflowing `mission_plant_observations.gps_distance_m`
(`numeric(8,3)`). The observation transaction failed.

- Read GPS with Pillow, which is already a required service dependency. Validate
  coordinate references, DMS components and WGS84 ranges.
- Missing or invalid EXIF GPS now stops the disease request with HTTP 422 before
  inference/export. No zero-coordinate fallback is generated. Explicit GPS at
  `(0,0)` remains distinguishable from missing metadata.
- The BE validates the nearest-pole distance before persistence, including
  rounding at the `numeric(8,3)` boundary. Invalid/unrepresentable distances return
  `DetectDiseases.InvalidLocation` instead of a PostgreSQL overflow. The whole
  transaction rolls back; distances and coordinates are not clamped or fabricated.
- No schema migration, map reconstruction or payment changes are needed.

## Verification

Run from `backend/services/metashape-service` using the AI environment:

```powershell
python -m unittest discover -s tests -p test_disease_gps.py -v
```

The five Python tests cover reading GPS without piexif, hemispheres, missing or
invalid metadata, explicit zero coordinates and blocking inference/storage for
unlocated images. They do not start reconstruction or call real object storage.

Run from the BE repository:

```powershell
dotnet test backend/tests/AgriDrone.UnitTests/AgriDrone.UnitTests.csproj --no-restore --filter "FullyQualifiedName~DiseaseDetectionGpsTests|FullyQualifiedName~MetashapeProcessingTests"
```

Ten distance cases and eight existing processing tests pass. This includes the
actual 11,823,080m regression and values that overflow only after rounding.

The local Tam Vu 2 fixture contains 216 photos; all 216 GPS tags are readable with
the fixed extractor. A real call to the restarted local disease endpoint returned
HTTP 200: 216 images scanned, 61 detections, all coordinates in the Farm area.
Comparing those detections with the 80 active DB poles gave nearest distances of
0.117–2.865m (60 within the requested 2.5m matching tolerance). All distances fit
the existing column. The one outside tolerance stays unmatched; no tolerance was
increased to force a match.

The reconstruction route probe still returned HTTP 403. Verification did not
write observation runs to the BE database or publish results. AI CSV/crop outputs
were regenerated by real inference. BE persistence and subsequent human
review/publication still need to be retested after restarting the paused API.

## Retest in the app

1. Stop the paused/old API debug session, rebuild, and start the BE again. A request
   paused with the old `(0,0)` result does not pick up this change automatically.
2. Restart the AI service to load the Python fix. The local ready-map wrapper must
   continue blocking reconstruction; only its disease endpoint is needed here.
3. Refresh the Manager mission page and run disease detection again. Existing raw
   images do not need new GPS values or another upload for this fixture.
4. Inspect the new observation run before continuing review and publication.

GPS extracted from an image represents its EXIF capture position. This fix does
not add pixel-to-ground projection or claim that a camera coordinate locates
each visible fruit precisely. A missing timestamp/GPS cannot be repaired by
assigning an arbitrary telemetry point. Model provenance and catalog mappings
must still satisfy the existing review/publication rules.
